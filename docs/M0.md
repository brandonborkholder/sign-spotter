# M0 integration proof

Status: awaiting the deployed-origin Android probe and one legitimate report

Last updated: 2026-08-30

## Purpose

M0 determines the exact Loudoun/PublicStuff schema, whether the GitHub Pages
origin may call the metadata API directly, and whether submission is anonymous
or account-backed. It must not create a fake government report.

## Evidence established from the deployed county client

The current application served by `iframe.publicstuff.com` contains these
integration details:

- API base: `https://vc0.publicstuff.com/api/2.0/`
- Client header: `PublicStuff-Client: 1295`
- Client metadata: `GET city_view`
- Request schema: `GET requesttypes_list`
- Submission: `POST request_submit`
- Photo field: `uploadedfile`
- Request fields include `request_type_id`, `client_id`, `space_id`, title,
  description, coordinates/address, `has_image`, and JSON-encoded
  `custom_field_<id>` values.
- A signed-in submission adds `api_key`; the county client can advertise whether
  the selected request type allows an anonymous submission.

The public Swagger description at `https://api.publicstuff.com/apidocs`
documents a newer API that requires an issued Authorization API key. This
project does not have such a key and will not copy a secret into frontend code.
The probe therefore tests the same legacy read endpoints used by the county's
public iframe.

## Probe safety boundary

The M0 web page contains only two cross-origin `GET` calls. It has no submit
function and does not reference the `request_submit` route in runtime source.
It normalizes the response in memory and exports no raw response.

The export redacts credential/contact/location keys defensively. It still must
be inspected before committing. Raw HAR files must never be committed.

## Run on the final Pages origin

1. Publish the current build to GitHub Pages.
2. On the target Android phone, open the Pages URL in Chrome.
3. Tap **Run read-only probe**.
4. If both rows say **Readable**, review the detected request type and custom
   fields.
5. Tap **Download JSON**.
6. Inspect the JSON and place it in `fixtures/publicstuff-m0-1011942-redacted.json`.

If either request is blocked, connect the phone to a workstation and inspect it
at `chrome://inspect/#devices`. Record whether the Network panel shows a failed
`OPTIONS` preflight, a PublicStuff HTTP response, DNS/TLS failure, or another
cause. A JavaScript `TypeError: Failed to fetch` alone cannot distinguish CORS
from a network failure.

## Legitimate-report evidence

The read-only probe cannot prove upload CORS or final authentication. During the
next real sign violation:

1. Open the official county form with Network recording enabled.
2. Submit only a truthful report you intend the county to receive.
3. Save the request/response temporarily outside the repository.
4. Record only these normalized facts:
   - required submission field names;
   - custom field IDs and value encoding;
   - whether `api_key` was required;
   - whether the request was anonymous;
   - response shape and request ID field;
   - CORS response headers and whether a preflight occurred.
5. Delete the raw capture after the facts are transcribed and verified.

Do not record the photo, contact values, precise coordinates, address, session
token, or real request ID in a committed fixture.

## Exit criteria

M0 is complete when:

- the deployed probe has captured the real normalized request schema;
- direct metadata CORS is known from the GitHub Pages origin;
- anonymous/authentication behavior is known;
- one legitimate report has established the actual POST and response shape;
- direct, bounded-proxy, or capture-and-handoff has been selected and recorded.
